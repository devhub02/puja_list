# Content Schema (bundled JSON)

Status: designed in Phase 0, implemented in Phase 2 (Pydantic models in `backend/app/schemas/`, tools in `scripts/`); festival model and calendar pipeline revised in Phase 6A (`schemaVersion` 2, see §8). Source of truth lives in `content/`; Pydantic enforces it; the validated export is bundled in `mobile/assets/puja_data/`.

## 1. Conventions

### 1.1 Locale maps
Every user-visible string is a **locale map**: an object whose keys are BCP-47-style language codes and whose values are strings.

```json
{ "en": "Water for achaman", "hi": "आचमन के लिए जल" }
```

- `en` is **mandatory** in every locale map. Other languages are optional.
- Fallback order at display time: selected language -> `en`.
- Adding a language (for example `ta`, `bn`) means adding new keys to the maps and a language entry in the app's language list. It must need **no code changes** to the content model.
- Locale-map fields are written below as `LocaleMap`. Optional ones are `LocaleMap?`.

### 1.2 Stable ids
- Every entity has an `id`: a lowercase ASCII string matching `^[a-z0-9]+(_[a-z0-9]+)*$` (snake_case), for example `ganesh_chaturthi`, `sm_modak`.
- Ids are referenced by user data (saved pujas, checklist progress, custom samagri, reminders, history). **An id is never renamed and never reused**, even after the entity is removed. To retire an entity, set `"status": "deprecated"` (optionally with `replacedBy`) instead of deleting it.
- Recommended prefixes (conventions, not enforced beyond uniqueness): festivals `fest_`, pujas `puja_`, samagri `sm_`, vidhi steps `step_`, variations `var_`, checklist items `chk_`, calendar entries `cal_`.
- Ids are unique **per entity type** across the whole content set.

### 1.3 Shared enums

| Enum | Values |
|------|--------|
| `Classification` (samagri) | `REQUIRED`, `COMMON`, `OPTIONAL` |
| `ReviewStatus` | `ai_drafted`, `cross_checked`, `expert_verified` |
| `DateCertainty` | `confirmed`, `provisional`, `varies_by_region` |
| `EntityStatus` | `active`, `deprecated` |
| `Region` | `north`, `east`, `south`, `west`, `central`, `north_east`, `tribal_regional`, `pan_india` (used by pujas and variations) |
| `FestivalRegion` | `pan_india`, `north`, `east`, `west`, `south`, `central`, `north_east`, `himalayan`, `tribal` (used by festivals and by the `region` of a calendar entry) |
| `PujaCategory` | `festival`, `vrat`, `household`, `life_cycle`, `regional`, `tribal` |
| `FestivalCategory` | `deity_festival`, `harvest_seasonal`, `new_year`, `vrat_fasting`, `family_bond`, `nature_ritual`, `yatra_mela` |
| `DateType` | `fixed_gregorian`, `solar`, `lunar`, `regional`, `variable` (see §3.1) |

`Region`, `FestivalRegion`, `PujaCategory`, `FestivalCategory` and `DateType` are closed lists in the validator; extending them is a small, reviewed schema change. `Region` (pujas) was left as it was in Phase 6A; festivals use the separate `FestivalRegion` list, which adds `himalayan` and `tribal` and has no `tribal_regional`.

### 1.4 Meaning of classification
- `REQUIRED`: the puja is generally not performed without it according to the cited tradition.
- `COMMON`: widely used, but families/regions differ.
- `OPTIONAL`: customary extras. **Never auto-promoted** to a higher class by any code path.

Each puja owns its own samagri list; the same item id may be classified differently in different pujas (see §3.3).

## 2. Files

```
content/
  content_manifest.json     # contentVersion, language list, file list
  festivals.json            # Festival[]
  pujas/<puja_id>.json      # one Puja per file (embeds samagri usage, steps, variations)
  samagri.json              # SamagriItem[]  (shared catalogue: name, description)
  calendar/<year>.json      # CalendarYear (year-specific dates, kept separate; GENERATED from the CSV)
  calendar/calendar_dates.csv   # the only place dates are entered, by hand (see §7)
```

`content_manifest.json`, `festivals.json` and `samagri.json` are required (an empty list `[]` is valid). The `pujas/` and `calendar/` directories are optional: a missing directory means "none yet" (git cannot store an empty directory, and no placeholder files are created). A puja file must be named `<puja id>.json` and a calendar file `<year>.json`. `calendar/<year>.json` files are generated by `scripts/import_calendar_dates.py` from `calendar/calendar_dates.csv`; do not edit them by hand. The CSV is not a JSON file and is not part of the bundle (§7).

### 2.2 Exported bundle

Metro (the React Native bundler) cannot list files at runtime, so export merges everything into **one file**, `mobile/assets/puja_data/content.json`, written only by `scripts/export_content.py` after validation succeeded:

```json
{
  "checksum": "sha256:<hex>",
  "schemaVersion": 2,
  "contentVersion": 1,
  "languages": ["en", "hi"],
  "festivals": [],
  "pujas": [],
  "samagri": [],
  "calendar": []
}
```

- `pujas` holds the full puja objects (samagri usage, steps, variations, checklist embedded); `calendar` holds the `CalendarYear` objects.
- Keys are camelCase exactly as in the source files; optional fields that are `null`/absent are omitted. Lists are sorted by id (calendar by year) so the output is deterministic.
- `checksum` is SHA-256 over the canonical JSON (sorted keys, compact separators, UTF-8) of everything except `checksum` itself.
- The app re-seeds when `contentVersion`, `schemaVersion` or `checksum` differs from what it stored.

### 2.1 Manifest

```json
{
  "contentVersion": 1,
  "schemaVersion": 2,
  "languages": ["en", "hi"],
  "calendarYears": [2026]
}
```

- `contentVersion` (integer >= 1, increases on every content release) drives re-seeding in the app.
- `schemaVersion` is bumped only when the JSON structure itself changes.

## 3. Entities

### 3.1 Festival

A festival is a calendar entry in its own right. It **may exist without a puja guide** (a calendar-only festival): `linkedPujaIds` is optional and, when given, every id must exist.

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | stable id |
| `name` | LocaleMap | standard festival name; `en` and `hi` required |
| `alternateNames` | `AltNames` (optional) | search aliases in English and Hindi, see §3.7 (this is the `searchTerms` mechanism; there is no separate field) |
| `shortDescription` | LocaleMap | 1 to 2 sentences, own words; `en` and `hi` required |
| `significance` | LocaleMap (optional) | longer text, own words; `en` and `hi` when present |
| `regions` | FestivalRegion[] | at least one, from the fixed list in §1.3 |
| `states` | LocaleMap[] (optional) | free-text state names (`{"en": "Odisha", "hi": "ओडिशा"}`) where the festival is mainly observed |
| `category` | FestivalCategory | fixed list in §1.3 |
| `dateType` | DateType | how the date is determined, see below |
| `observanceDescription` | LocaleMap (optional) | lunar month/tithi or season **in words**, only when confidently known. It must tell the reader to check a local panchang (validated: `en` contains "panchang", `hi` contains "पंचांग") |
| `linkedPujaIds` | string[] (optional) | puja guides for this festival; each must exist |
| `reviewStatus` | ReviewStatus | required; the UI labels anything not `expert_verified` |
| `sourceNote` | LocaleMap | where/how the entry was prepared and checked; required, `en` and `hi` |
| `status` | EntityStatus | default `active` |
| `replacedBy` | string? | id of the festival that replaces a `deprecated` one |

`dateType` values:
- `fixed_gregorian`: falls on (about) the same Gregorian date every year. Available in the schema; the Phase 6A catalog uses none, because festivals normally attributed to a Gregorian date are in fact solar.
- `solar`: tied to the Sun's movement (Sankranti-type festivals, solar new years); the Gregorian date shifts only by a day or so.
- `lunar`: set by a lunar month and tithi (most festivals); the Gregorian date moves each year.
- `regional`: the date is set by a regional calendar or local custom and differs between regions or traditions (for example star-based or regional-month festivals).
- `variable`: no single annual rule; announced or decided locally each year, or performed whenever a family chooses.

Festival metadata contains **no year-specific dates**. Dates live only in the calendar files (§3.6). A puja's `festivalId` (§3.2) is its primary festival and must be listed in that festival's `linkedPujaIds`; a festival may also list a puja whose `festivalId` names another festival.

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | stable id |
| `festivalId` | string? | optional link to a festival |
| `name` | LocaleMap | |
| `alternateNames` | `AltNames` (optional) | search aliases, see §3.7 |
| `category` | PujaCategory | |
| `regions` | Region[] | at least one |
| `summary` | LocaleMap | |
| `significance` | LocaleMap | own words |
| `samagri` | SamagriUsage[] | see §3.3 |
| `steps` | VidhiStep[] | see §3.4 |
| `variations` | RegionalVariation[] | see §3.5 |

### 3.3 Samagri (shared catalogue + per-puja usage)

Catalogue entry (`samagri.json`), puja-independent:

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | stable id |
| `name` | LocaleMap | |
| `alternateNames` | `AltNames` (optional) | search aliases, see §3.7 |
| `description` | LocaleMap (optional) | what the item is |
| `status` | EntityStatus | default `active` |
| `replacedBy` | string? | id of the item that replaces a `deprecated` one |

Per-puja usage (`SamagriUsage`, inside a puja file), puja-specific:

| Field | Type | Notes |
|-------|------|-------|
| `samagriId` | string | must exist in the catalogue |
| `classification` | `REQUIRED` \| `COMMON` \| `OPTIONAL` | exactly one value |
| `purpose` | LocaleMap | why it is used in this puja |
| `quantityGuidance` | LocaleMap (optional) | **never invented**; unknown -> omit or "as needed" |
| `preparationNote` | LocaleMap (optional) | |
| `regionalNote` | LocaleMap (optional) | regional/family difference stated as a difference |
| `sortOrder` | integer | ordering within the puja's list |

### 3.4 Vidhi step

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | stable id (unique across all pujas) |
| `stepNumber` | integer >= 1 | consecutive within the puja, starting at 1 |
| `title` | LocaleMap | |
| `description` | LocaleMap | own words |
| `relatedSamagriIds` | string[] | each must appear in this puja's `samagri` |
| `isOptional` | boolean | |
| `importantNote` | LocaleMap (optional) | |

Mantras/verses are **not** part of Phase 0. If added later they must be a separate, sourced field; text is never invented.

### 3.5 Regional variation

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | stable id |
| `regions` | Region[] | where this practice is common |
| `title` | LocaleMap | |
| `description` | LocaleMap | presented as "in some regions/families", never as the universal rule |
| `affectsStepIds` | string[] (optional) | steps in this puja |
| `affectsSamagriIds` | string[] (optional) | samagri in this puja |

A variation exists only inside its puja's file, so it always belongs to an existing puja; its `affects*` ids are checked against that puja.

### 3.6 Calendar dates (separate file per year)

`content/calendar/<year>.json`:

```json
{
  "year": 2026,
  "entries": [
    {
      "id": "cal_2026_example",
      "festivalId": "fest_example",
      "date": "2026-01-01",
      "endDate": null,
      "region": "all",
      "certainty": "provisional",
      "regionNote": { "en": "Date can differ by region/panchang." },
      "source": "verified panchang reference name"
    }
  ]
}
```

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | stable id |
| `festivalId` | string | must exist in festivals |
| `date` | `YYYY-MM-DD` | the date as bundled and verified; **never computed in code** |
| `endDate` | `YYYY-MM-DD` or null | for multi-day observances; must stay in the file's year |
| `region` | string | `all` (default) or one `FestivalRegion` value; a festival can have one entry per region per year |
| `certainty` | DateCertainty | required: `confirmed` (checked against a named authoritative source), `provisional` (from a source but not cross-checked), `varies_by_region` (the date genuinely differs by region/tradition; use one row per region) |
| `regionNote` | LocaleMap (optional) | |
| `source` | string | where the date was verified |

If a festival has no entry for a year, the app shows "date not available". The app and tooling never derive tithi/lunar dates.

Entry ids are generated by the importer as `cal_<year>_<festival id without "fest_">`, with `_<region>` appended when the region is not `all`.

### 3.7 Search aliases (`alternateNames`)

`AltNames` is `{ "<lang>": ["spelling", ...] }`, available on festivals, pujas and samagri items. It is the search-alias mechanism, so no separate `searchTerms` field exists.

- Aliases are **search-only**: they are indexed but never displayed. (Names to show to users belong in `name`.)
- Put Latin-script variants of a Hindi word under `en` (`"en": ["Laxmi", "Lakshmi Pujan"]`) because people type Hindi in Roman letters, and Devanagari spelling variants under `hi` (`"hi": ["लक्ष्मी पूजन", "लक्षमी पूजा"]`).
- Aliases are authored in content. The app and tools never guess or transliterate spellings.
- Keys must be languages listed in the manifest; values must be non-empty strings.

## 5. Standard disclaimer

Shown on every puja unless overridden. Hindi text (from project rules):

> Vidhi aur samagri region, family tradition, sampradaya aur puja ke tareeke ke hisaab se alag ho sakti hai. Apni family tradition ke anusaar changes karein.

It is stored as a locale map (`en` + `hi`) in the app's string resources, not duplicated in each puja.

## 6. Validation rules (enforced by Pydantic in `scripts/` / `backend/`)

1. **Locale maps**: every `LocaleMap` is an object with at least the key `en`, and every value is a non-empty string. Keys look like language codes (`en`, `hi`, `pt-BR`) and must be in the manifest `languages` list (this also applies to `alternateNames`). The manifest `languages` must include `en`.
2. **Unique ids**: ids are unique within their entity type across all files (festival, puja, samagri, step, variation, checklist item, calendar entry). Id format matches `^[a-z0-9]+(_[a-z0-9]+)*$`.
3. **Id stability**: a release must not remove or rename a festival, puja, samagri or checklist-item id present in the previous release (these are the ids user data can point at). Retire them with `status: deprecated` instead (checklist items have no status and simply stay). Step and variation ids are not referenced by user data and may change. `contentVersion` must never go down, and changed content must have a higher `contentVersion` than the previous export. All three are checked by `export_content.py` against the previous `mobile/assets/puja_data/content.json`.
4. **Classification**: each `SamagriUsage.classification` is exactly one of `REQUIRED | COMMON | OPTIONAL`. No other value, no list, no missing value.
5. **Samagri references**: every `samagriId` in a puja exists in the catalogue; every `relatedSamagriIds` entry in a step exists in **that puja's** `samagri` list; every `affectsSamagriIds` / `affectsStepIds` in a variation exists in that puja.
6. **No duplicate samagri** within one puja (`samagriId` appears at most once).
7. **Step numbering**: `stepNumber` values in a puja are exactly 1..N with no gaps or duplicates.
8. **Sort order**: `sortOrder` is an integer, unique within a puja's samagri list.
9. **Review fields**: `reviewStatus` is one of the three enum values; `sourceNote` is present with an `en` entry.
10. **Regions/category**: values come from the closed enums; `regions` is non-empty.
11. **Festival references**: `festivalId` on a puja points to an existing festival whose `linkedPujaIds` lists that puja; every id in a festival's `linkedPujaIds` exists (the list may be empty: calendar-only festival) and has no duplicates.
12. **Calendar**: `festivalId` exists; `date` (and `endDate`) is a valid ISO date within the file's `year`; `endDate >= date`; `certainty` present; `region` is `all` or a `FestivalRegion`; at most one entry per festival per region per year.
13. **No year-specific dates outside calendar files**: festival/puja models have no date fields and unknown fields are rejected (rule 15), so a date cannot be added there.
14. **Content version**: `contentVersion` on each puja is an integer `<=` the manifest `contentVersion`.
15. **Unknown fields are rejected** (strict models) so typos do not silently pass.
16. **Files**: required files exist and are valid UTF-8 JSON; a puja file is named after its `id`, a calendar file after its `year`; manifest `calendarYears` equals the calendar files present; manifest `schemaVersion` is one the tooling supports; no unknown `*.json` files sit in `content/`.
17. **`replacedBy`** (when present) points at an existing entity of the same type.
18. **Festival text in both languages**: `name`, `shortDescription`, `sourceNote`, and (when present) `significance`, `observanceDescription` and every `states` entry need an `hi` entry as well as `en`. (Other entities keep the general rule: `en` mandatory.)
19. **Observance wording**: a festival's `observanceDescription` must tell the reader to check a local panchang (`en` contains "panchang", `hi` contains "पंचांग"); no festival text states an exact date.

Rules about *meaning* (not invented mantras, no copied text, quantities not guessed) cannot be machine-checked; they are enforced by review via `reviewStatus` and `sourceNote`.

## 7. Calendar date pipeline (Phase 6A)

Dates are **never** written by tooling, never computed and never typed into festival files. They enter the project only through `content/calendar/calendar_dates.csv`, filled by a person from verified sources (step-by-step guide: `docs/CALENDAR_DATA_GUIDE.md`).

```
content/festivals.json --scripts/export_dates_template.py--> content/calendar/calendar_dates.csv   (dates EMPTY)
        (a person fills date, certainty, source_note)
content/calendar/calendar_dates.csv --scripts/import_calendar_dates.py--> content/calendar/<year>.json
        -> scripts/validate_content.py -> scripts/export_content.py -> mobile/assets/puja_data/content.json
```

CSV columns: `festival_id, festival_name_en, year, date, end_date, region, certainty, source_note`.

- The template has one row per festival per supported year (2026 and 2027). If the CSV exists, a merge appends rows for festival/year pairs that are not in it yet; existing rows are never changed or removed.
- The importer ignores rows with an empty `date`. For every filled row it checks: `festival_id` exists; `date` is a real `YYYY-MM-DD` date; the `year` column equals the date's year; `end_date` (optional) is a real date, not before `date`, in the same year; `region` is `all` (a blank cell counts as `all`) or a `FestivalRegion`; `certainty` is present and one of the `DateCertainty` values; `source_note` is present; no two filled rows share festival + year + region. Problems are printed with the CSV line number and **nothing is written** unless every row is valid.
- On success it writes `calendar/<year>.json` for each year with at least one date (and removes the generated file of a year in the CSV that no longer has any), and keeps the manifest's `calendarYears` equal to the files present. It never changes `contentVersion`: bump it yourself before validating and exporting.
- With an empty CSV the pipeline succeeds with 0 dates, and the app shows "date not available".

## 8. Schema changelog

### schemaVersion 2 (Phase 6A)
Changed `Festival`:
- `description` renamed to `shortDescription` (1 to 2 sentences); `significance` is now optional.
- `pujaIds` renamed to `linkedPujaIds` and is optional (calendar-only festivals); the rule that each linked puja must point back through `festivalId` was dropped (a puja has one primary `festivalId`, a festival may list more pujas).
- New required fields: `category`, `dateType`, `reviewStatus`, `sourceNote`. New optional fields: `states`, `observanceDescription`.
- `regions` uses the new `FestivalRegion` list (adds `himalayan`, `tribal`).
- New validation rules 18 and 19.

Changed `CalendarEntry`: new `region` field (default `all`); the duplicate rule is now "one entry per festival per region per year" (was "per festival per date").

New enums: `FestivalRegion`, `FestivalCategory`, `DateType` (§1.3). The mobile app supports `schemaVersion` 2 only (the bundled content is always built with the app); the phone database changes are in `docs/DB_SCHEMA.md` (migration `0003_festival_catalog`).
